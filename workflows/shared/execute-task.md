## Input

開始前必須取得：

- issue ID，以及 README 的 `**分級**` 與 `**風險**`
- 明確指定的步驟（Small / Medium）或 Phase / Task（Large）
- 該項目的預期產出、完成判準與驗證方式
- 任務文件「風險與首要驗證」或「Risk Decision」中的完成證據
- 專案現有程式碼與可用的驗證入口
- 指定項目對應的驗收標準（Medium / Large 為 Scenario ID 與 Gherkin 及其外迴圈、內迴圈定義；Small 為輕量驗收條件與各步驟的驗證方式，測試層級與命令於執行時決定）
- 該項目是否會改變可觀察行為；標為不改變者需取得其等價證據定義

任一必要輸入缺漏時，列出缺項並停止實作；先回到規劃階段補齊，不自行猜測完成條件。

## Execute Scope

任務清單來源依 issue 分級而定（分級規則的權威定義見 `docs/AGENTS.md`「文件動態分級規範」，下表為摘要）：

| 分級 | 任務清單來源 | 執行對象 |
|---|---|---|
| Small | `README.md` 的「實作與驗證步驟」 | 指定的**步驟** |
| Medium | `implementation-plan.md` 的「實作步驟」 | 指定的**步驟** |
| Large | Implementation Plan Decomposition | 指定的 **Phase / Task** |

目標：只實作指定項目，取得可重複驗證的完成證據，並回寫權威任務狀態。

風險已在規劃階段決定任務順序。執行時不得自行重排或改寫已核准的風險策略，只執行目前指定的步驟 / Task；若必要風險資訊缺漏，先回到規劃階段補齊。

執行時必須遵守：

* 僅實作當前指定的 Task
* 不應修改與任務無關的模組
* 必須遵守既有架構設計
* 產出的程式碼可直接整合至專案

## Execute Tasks

1. **確認工作分支**

   * 檢查當前分支：若位於 main / master 等主幹分支，先建立並切換至 issue 分支再開始實作
   * 分支命名：以 `issue-{ID}` 開頭，可加簡短描述後綴（如 `issue-101-oauth-login`）
   * 分支名稱必須包含 issue ID，供 `dev-cycle` 狀態偵測使用

2. **確認任務契約**

   * 讀取指定項目的目標、預期產出、完成判準與驗證方式
   * 確認相關模組、檔案及尚未完成的相依任務
   * 若當前任務是首要驗證，確認預定的完成證據
   * 確認每項驗收標準都有核准內容；Medium / Large 另確認計畫已定義外迴圈 / 單元測試路徑、紅燈命令與預期失敗原因，Small 依 AC 的檢查方式於執行時決定測試層級與命令
   * 採完整 Gherkin 時，依 `docs/AGENTS.md`「規格修訂的查核」比對 issue README，並更新受影響 Scenario 的核准狀態；Small + Medium / High 的輕量驗收條件套用同一查核，受影響條目標註 `（待重新核准）` 後回到 `new-issue`
   * Small 且風險為 Medium / High 時，確認本次項目對應的條件已寫出失敗路徑；缺漏時回到規劃階段補齊，不得自行補寫未核准的失敗行為
   * 本次指定項目對應的 Scenario 狀態為 `待核准` 或 `待重新核准` 時不得實作，回到 `new-issue` 取得核准；其他 Scenario 為 `待核准` 或 `待重新核准` 不阻擋本項目（狀態定義見 `docs/AGENTS.md`「分批核准」）
   * 相依任務未完成或契約不完整時，說明阻塞並停止

3. **分析現有程式碼**

   * 找出相關模組與既有邏輯
   * 確認現有設計模式
   * 找出可能受影響的既有行為與驗證方式

4. **判定任務類型並進入對應流程**

   * 先判定本次任務是否會改變可觀察行為：
     - **會改變**：依步驟 5 至 9 執行紅燈、綠燈、重構
     - **不會改變**（純重構、純文件）：跳過步驟 5 至 8，依下方「不改變可觀察行為時的等價證據」取得證據，再回到步驟 9 至 11
   * 會改變行為且 Superpowers 可用時，優先調用 `test-driven-development`（選用增強）；未安裝時直接執行步驟 5 至 8 的內建等價流程
   * Small 且外迴圈與內迴圈落在同一測試層級時，依 `docs/AGENTS.md`「紅綠重構證據」的單迴圈合併規則將步驟 5 與 6 合併為一次紅燈，並記錄「為何此層級即為該行為的可觀察層級」；層級確實分開時仍走雙迴圈
   * 本流程中的 production code 包含應用程式原始碼、執行期設定、資料庫 migration 與會改變產品行為的資產；測試、feature / Step Definitions 與純測試 fixture 不屬於 production code

5. **BDD 外迴圈紅燈**

   * 先建立或補齊 Gherkin 自動化測試與 Step Definitions 殼，不得先修改 production code
   * 專案沒有 BDD runner 時，改以標註驗收標準編號的整合或端對端測試充當外迴圈，並記錄採用的替代方式；不得因缺少特定工具而省略外迴圈
   * 執行指定外迴圈命令，確認它因尚未實作的目標行為失敗，而不是因語法、環境或無關錯誤失敗
   * 記錄驗收標準編號、命令、exit code 與關鍵失敗輸出；未取得相關紅燈證據時立即停止

6. **TDD 內迴圈紅燈**

   * 針對驅動目標行為的最小底層單元撰寫一個測試
   * 執行精準測試命令，確認它因缺少目標行為失敗
   * 記錄測試名稱、命令、exit code 與關鍵失敗輸出；測試一開始就通過時，先檢查測試是否真的覆蓋缺少行為，不得把綠燈冒充紅燈

7. **最小綠燈實作**

   * 只有步驟 5 與 6 都有有效紅燈證據後，才能修改 production code
   * 只撰寫讓當前單元測試與 BDD Scenario 通過的最少程式碼，遵守既有架構與命名規則
   * 依序執行單元測試與 BDD 命令，記錄綠燈輸出

8. **綠燈下重構**

   * 只有單元測試與 BDD Scenario 都已綠燈時才可重構
   * 改善本次新增程式碼的命名、重複與結構，不擴張 Task 範圍
   * 重構後重新執行單元測試、BDD Scenario 及相關回歸檢查，任一失敗就回復未完成狀態

9. **假綠燈檢查**

   * 依 `docs/AGENTS.md`「假綠燈」逐項確認本次沒有製造假綠燈
   * 需要修改測試契約時先停止並記錄真實理由（行為已變更／測試本身錯誤／使用者要求豁免）
   * 使用者明確要求修改或移除測試時照做，但**不得記錄成驗證通過**
   * 本次證據若有持久力限制（探針或斷言綁在易變字串、日誌訊息等細節上），主動於證據中揭露並附更穩固的替代做法；依 `docs/AGENTS.md`「證據持久力」，揭露不構成假綠燈也不扣分

10. **驗證完成條件**

   * 先從專案規則與設定找出可用的 build、test、lint、typecheck 或等效檢查
   * 執行指定 Task 的驗證方式及所有與本次變更相關的檢查
   * 逐項核對完成判準；每項都必須有可觀察的通過證據
   * 記錄每個命令或檢查、實際結果，以及未執行項目的原因與殘餘風險
   * 若當前任務是首要驗證，記錄實際觀察結果、執行方式及是否符合預定完成證據
   * 不得只寫「已驗證」；證據必須包含可重複確認的命令結果、測試輸出、樣本觀察或等效資訊
   * 判準為生產環境觀測時，依 `docs/AGENTS.md`「觀測式驗收」執行：先以對照組驗證判準本身、回答「若這件事失敗了，這個判準會不會仍然是綠的？」、記錄取數時間與範圍及查詢原文；答不出「不會」時先改判準，不得逕行結案
   * 逐一列出各驗收標準編號的紅綠重構證據；不改變可觀察行為的任務改列等價證據

11. **回寫權威狀態**

   * 在原任務清單將本次指定步驟 / Task 標記為已完成
   * 在同一任務項目記錄驗證方式與實際證據
   * 本次若發生語意事件（規格修訂、文件敘述被推翻等），以系統當下日期補記 README Timeline；單純完成步驟不逐筆記 Timeline，進度由任務清單狀態表示
   * 依 `docs/AGENTS.md`「常青文件更新責任」確認本次變更是否觸發 `architecture/`、`domain/`、`operations/` 等常青文件；有觸發時一併更新，並把「最後驗證」之類的日期標頭改為系統當下日期
   * 若實作後現況與舊文件不同，以帶日期的 `> [!NOTE]` 補充，不覆寫歷史描述；issue 文件不另行維護檔尾 Changelog

只有完成判準、必要驗證與文件回寫全部通過，本次 Task 才算完成。任一項失敗時保留未完成狀態，並回報阻塞與下一步。

### 不改變可觀察行為時的等價證據

步驟 5 至 8 的紅燈要求只適用於會改變可觀察行為的任務。純重構改記變更前後執行**同一組**既有測試的全綠輸出；純文件、排版或無可執行行為改記可重複的靜態檢查或明確手動步驟與不適用理由。兩者的完整條件（含既有測試不足以覆蓋被重構行為時，須先補 characterization test 並取得綠燈）依 `docs/AGENTS.md`「不改變可觀察行為的任務」，不得因此省略驗證。

將任務判為不改變可觀察行為，等同承諾其 diff 不含行為變更。實作過程中若發現必須改變行為，立即回到步驟 5 補齊紅燈證據，不得沿用等價證據結案。

### Gate 豁免

使用者明確要求跳過本 skill 的某項 gate（例如「不用先寫測試」）時照做，並依 `docs/AGENTS.md` 在 issue README 的 `## Gate 豁免紀錄` 記錄日期、豁免項目、使用者原話與殘餘風險。不得自行推定豁免，也不得把被豁免的驗證記錄成已通過。

## Output

只在對話輸出本次結果，不另外建立實作報告，也不在 issue 文件複製完整程式碼：

```markdown

# Task Result

## Phase

<Phase 名稱；Small / Medium 可省略此區塊>

## Task

<Task 名稱，或 Small / Medium 的步驟名稱>

## Summary

（簡要說明本次實作內容）

## Implemented Changes

* 說明新增或修改的功能
* 說明關鍵設計決策

## Modified Files

* path/to/file1
* path/to/file2

## Verification Evidence

* 完成判準與結果
* 驗收標準編號與對應內容（Scenario ID 與 Gherkin，或 AC 編號與條件）
* 外迴圈紅燈命令、exit code 與失敗原因
* 單元測試紅燈命令、exit code 與失敗原因
* Small 單迴圈合併時：以合併紅燈命令與層級選擇理由取代上兩行
* 最小實作後及重構後的全綠命令與結果
* 不改變可觀察行為時：變更前後同一組測試的全綠輸出，或替代檢查與不適用理由
* 未執行項目、原因與殘餘風險（沒有則省略）
* 本次適用的 Gate 豁免（沒有則省略）

## Document Updates

* 原任務狀態
* README Timeline（僅語意事件，若有）
* 帶日期的 `> [!NOTE]` 補充說明（若有）

```

## 注意事項

* 僅實作指定的步驟 / Task
* 避免同時處理多個步驟 / Task
* 若任務依賴尚未完成的步驟 / Task，需明確指出
* 若發現架構問題或設計衝突，需在 Summary 中說明
* 文件回寫失敗時不得將 Task 標記為完成
