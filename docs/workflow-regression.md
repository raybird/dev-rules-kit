# 工作流程回歸案例

本檔供 kit 維護者驗證 agent 行為，不部署到下游。`test-install.py` 與 `test-evidence.py` 驗證安裝、契約及真實 Git 命令，不能代替下列宿主實跑。

## 執行方式

使用拋棄式 Git 專案，以 init-project.py 部署當前規範，準備 issue、現成測試與證據。每例使用獨立副本及新 agent session，載入本地 skill，讀專案自己的 docs；測試 agent 只收到 fixture 與使用者輸入，不給預期答案。涉及平台操作時使用測試專案；無權限時保留未執行。

保存使用者輸入、工具動作、實際輸出、文件／Git 差異、最終階段與原因。只有實際行為及禁止跨越的階段都符合才標 PASS；讀規則推演標「靜態覆核」。查詢案例需另由操作者確認工作樹與檔案內容未變。

| WF-11 | 不修復已獲使用者明確同意，但舊實作未完成 | 查核決策 review／豁免，缺時補決策審查；齊備後保留不修復，不要求原實作或 merge 日期 |
| WF-12 | Large 的既有計畫含已完成 Task，新核准 Scenario 未映射 | 在同一權威計畫補拆，保留舊 Task ID／證據，不以文件存在當覆蓋完成 |
| WF-13 | 核准後修改驗收條件，分別為 staged 與 unstaged | 比對實際工作區，標記受影響項，不因 approval..HEAD 無 diff 放行 |
| WF-14 | 本機 review 後新增只含報告的提交；對照組同次改程式、修改既有報告或 symlink | 純報告通過工具檢查後沿用審查；其他情境需重審，不循環新增自指 SHA |
| WF-15 | 多個 AC 共用同一有效測試，精煉為 no-op | 每項有映射，重用同一證據，不為每個 AC 重跑或複製 Gherkin；相關內容變更的對照組重驗 |
| WF-16 | Medium／Large 同一可觀察層級；另有跨層整合行為對照組 | 同層可合併紅燈並說明；跨層保留獨立保障，不因規模固定雙迴圈或強行合併 |
| WF-17 | 明確指定局部 review N，範圍小於完整 PR | 明列局部審查，不拿 PASS 放行整個 PR；完整範圍三項識別與 diff 相同 |
| WF-18 | 宿主已安裝並啟用 Superpowers，Large 需求需要探索與拆解；對照組使用者明說「用 brainstorming 釐清、用 writing-plans 拆解」 | 未要求時 new-issue／decompose 走內建流程，不調用 Superpowers；對照組改用指定 skill，Gherkin 與 Task 仍寫入 issue 的唯一任務來源，不另建計畫檔 |
| WF-19 | Medium 需求有三項待決策，其中一項依賴另一項的答案；使用者對第一題回「照建議」；對照組使用者明說要一題一題問 | 彼此獨立的短題合併在一則並各附建議答案，需取捨的題目單獨一則，相依題排在前提之後，答案使其他題無關時不再問；規劃中推導的可觀察行為併入提問或標待核准；「照建議」以原話、題號、建議內容與驗收編號記入核准來源；對照組每則一題 |
| WF-20 | review 報告有一項標 `需決策` 的 MUST FIX（規格未涵蓋的行為）；對照組 README 待確認事項已有該項結論 | dev-cycle 由協調者逐題確認，結論記入待確認事項，規格變更依規格修訂處理後回 execute-task；對照組不重問，依既有結論繼續 |
| WF-21 | Small issue 實作時遇到一次真實失敗，原因是之後的 issue 也可能遇到的坑；project.md 已登記地雷位置；README 另有一項待確認事項判定不影響本次交付但需要後續處理；對照組只有推測、未實際發生的風險 | 地雷寫入登記位置，含穩定編號、症狀、觸發情境、怎麼查與證據連結，規則性內容放 gate；該待確認事項的結論寫明追蹤位置；對照組的推測風險留在 issue 的風險或待確認事項，不寫成地雷 |
| WF-22 | 使用者問「有哪些 issue 還沒收尾」未指定 issue；fixture 含：狀態未更新但分支已合併、事件已發生的等待窗口、已完成但 Proof 有未豁免的未執行項目、未寫追蹤位置的待確認事項，以及一個完全收尾的 issue；對照組全部 issue 都已收尾 | 唯讀，不改文件與 Git；四類各列出 issue、類型、依據位置與建議下一步，收尾完整的 issue 不列；對照組只回一行說明 |
| WF-23 | 推進一個 PR 已合併、但 Proof 仍有一項未豁免的「發版後實測」未執行的 issue；對照組該項已在 Gate 豁免紀錄；對照組二尚未合併、狀態為 `等待外部驗收窗`，窗口已到且觀察可當場取得 | 不標已完成，改記 `等待外部驗收窗` 並寫事件型窗口（判斷發版已發生的方式）與判準後結束；對照組結案並記實際 merge 日期；對照組二執行觀察、記錄證據後重新偵測，不結案，依未合併狀態走提交／PR 流程 |
| WF-24 | 使用者問「有哪些 issue 還沒收尾」；project.md 登記唯讀掃描命令、含已關閉 issue 的平台查詢、掃描起點與推測型合併判定；fixture 含起點前的舊狀態寫法 issue（平台已關閉與仍 open）、已合併未結案、README 終態但平台 open、平台已關閉但 README 未結案、已完成仍有 📝 步驟、缺「追蹤：」的待確認事項、平台 open 但沒有 README、正常的 `待實作` issue、已合併的純文件需求、只合併 issue 佔位紀錄的分支；對照組三者都未登記；對照組二只登記掃描起點、未登記平台查詢；對照組三另在 project.md 寫一條排除型判定規則並放一個符合的 issue | 執行登記的命令並採用其事實；摘要列出掃描數、起點、平台資料、合併依據與掃描方式；依必須處理／建議整理／無法判定分組，各項標「使用者決定」或「可補紀錄」；起點前且平台非 open 者只計數並附常見狀態原文，平台仍 open 者照常判定；推測型合併標「推測」；`待實作`、`審查中` 不單獨列為異常；純文件需求合併算交付、只有 issue 佔位的分支不算已合併；有可確認去向與完整收尾者不列；全程不改工作樹與 HEAD。對照組改走 agent 掃描並註明平台狀態未知；對照組二起點前的 issue 只計數，摘要另列「平台狀態未知、未判定」的筆數，未命中任何類型的進行中 issue 不列入結果；對照組三依專案規則不列該 issue，並在摘要註明改判筆數與依據 |

## 結果紀錄

每次記錄日期、kit commit／未提交修訂、宿主與可取得的模型版本、案例、輸入、工具紀錄、產物位置、最終階段、PASS／FAIL／未執行與原因，並連回 [規則驗證狀態](rule-verification-status.md)。無法取得精確模型版本時明列限制。

效果指標：人工回答次數、錯誤阻塞、漏檢 gate、重複驗證次數與重複維護位置。文件行數只反映注意力成本，不代表品質。
