# 規則驗證狀態

> **本檔是 kit 自身的維護紀錄，不是給下游複製的規範。** 下游要複製的是 `docs/AGENTS.md`。

## 這份文件存在的理由

2026-08-18 一天內連發 v2.6.0 至 v2.9.0，其中**三個缺陷是規則寫得完整、但根本執行不了**：

| 版本 | 缺陷 | 為什麼靜態閱讀看不出來 |
|---|---|---|
| 2.7.0 | 分批核准時誤用單行核准表 | 條件與展開時機都寫了，讀起來完全正確；但查核掃的是 `待核准` 字串殘留，收斂成單行後掃不到即視為通過——規則靜默失效 |
| 2.8.0 | 回填驗證對象寫成 `HEAD` | 命令合法且會回傳成功，只是驗錯對象：在尚未刪除的 issue 分支上驗證會通過，SHA 日後照樣失效 |
| 2.9.0 | 核心層齊備性檢查缺一端 | 檢查邏輯自洽，但只定義了 `docs/AGENTS.md` 這端的版本，skill 那端沒有標記，agent 無從比對 |

三者都是**當天剛寫的規則**，在紙上都成立，是有人真的去執行才垮的。靜態審查能檢查規則自不自洽，檢查不了它可不可執行。

因此每條規則都必須標明**是否被實際執行過**。未標為已驗證的規則，應被視為「可能有同類缺陷、尚未被發現」，而不是「已經生效」。

## 狀態定義

| 狀態 | 意義 |
|---|---|
| **已實跑驗證** | 有人在真實 issue 中執行過該規則，並產生可指認的結果 |
| **本地測試驗證** | 以負向測試確認守門確實會失敗（適用腳本類檢查） |
| **來源為實跑** | 規則的**動機**來自實跑發現的問題，但**規則本身**尚未被套用過 |
| **僅靜態撰寫** | 從閱讀與推理產出，尚無人執行過 |
| **曾失效並修正** | 交付後在實跑中被發現執行不了，已修正；修正本身的驗證狀態另計 |

## 已知的驗證限制

- **樣本數 n=2，且同源**：line-oa-plus 與 googleBooking 同屬一位使用者、跑同一套 kit、工作流程相近。**兩者共有的盲點照不出來**——例如多人並行 review、非中文協作者、非 Firebase 系技術棧的情境，今天完全沒有覆蓋。
- **回饋迴路是人力密集且一次性的**：2026-08-18 這輪靠逐一發訊息與回報完成，repo 內沒有任何機制保證下次改動時下游會回報。
- **規則總量淨成長**：`docs/AGENTS.md` 686 → 780 行、`rules/AGENTS.md` 222 → 234 行、六支 skill 合計 869 → 912 行。v2.6.0 的前提是「規則量本身有成本」，當日稍後的增補雖都有實跑證據支撐，但成本仍然存在。
- **今日新規則的缺陷率偏高**：四個版本中出現三個「執行不了」的缺陷，且全部是當天新寫的規則。依此推斷，**標為「僅靜態撰寫」與「來源為實跑」的條目中，很可能仍有尚未被發現的同類缺陷**。

## 維護方式

- 新增或修改規則時，在對應版本區塊加一列，預設狀態為「僅靜態撰寫」。
- 收到下游實跑回饋時，更新狀態並寫明**可指認的來源**（專案、issue 編號、日期、觀察到的具體結果）；不接受「應該可行」這類無來源的升級。
- 規則在實跑中被發現執行不了時，標為「曾失效並修正」並保留原因——那是這份文件最有價值的部分。
- 日期一律使用系統當下日期，格式 `YYYY-MM-DD`。
