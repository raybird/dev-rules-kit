**基準缺口**：q1 與 q4 的行為完全相同，使用者沒有要求逐題時，獨立短題同樣需要 4 則回覆，這是 S2 要改善的成本。

**核准紀錄（實跑發現）**：四例都以使用者原話與逐題回答作為核准來源，符合 acceptance.md「已接受具體方案」。但 agent 自行推導、未單獨詢問的可觀察行為，各例處理不一致：

| 案例 | agent 推導的行為 | 處理 |
|---|---|---|
| q1 | AC-2 標題含逗號、引號、換行時的 CSV 跳脫 | 寫成已核准，理由「CSV 本身的規則，屬原需求」 |
| q2 | AC-6 已完成不提醒、提醒反映指令後狀態、出錯不提醒 | 標待核准，記入 TBD-1 並詢問 |

expected.md 寫定的判準是「沒有核准原話時不得寫成已核准」。依此判準，q1、q3、q4 的推導項目不符，q2 符合；只看逐題回答的項目則四例都符合 acceptance.md。這是改規則前就存在的不一致，不是候選規則造成的。S2 是否處理，記入 README 待確認事項。

## 限制

- 每個掃描案例跑兩輪、提問案例一輪；單一宿主與模型。Codex、OpenCode、Antigravity、Cursor 未測，互動模式的 AskUserQuestion 路徑未測。
- 提問案例的回覆由操作者依固定答案表手動對應，「已完成項目是否匯出」「時區」這兩題因 agent 自行假設而沒有用到固定答案。
- 無遠端平台：合併以本機 `--no-ff` merge commit 代表，平台狀態來自 fixture 的模擬命令。
