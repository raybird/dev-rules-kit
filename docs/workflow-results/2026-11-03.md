## 觀察

- **回填問題只在「規格與實作分開提交」時出現**：28a、28c 的基準組在同一個 session 內實作時，本來就把回填併入實作提交；單獨回填提交只在 28d（只提交規格）出現。下游回報的回填成本落在這條路徑。
- **候選 28b 沿用的 PASS 本身有缺陷**：fixture 預先寫好的 PASS 報告把測試數寫成 4 個（實際 3 個），且「重複 id 不是本次引入」的理由不成立（`clear-done` 才讓重複 id 可能發生），測試也沒有經過 CLI 分派。基準組的記帳重審抓到測試數與 CLI 分派，候選 28b2 的重審抓到全部三項。這是 fixture 撰寫錯誤，判定標準已先提交，因此不修 fixture 重跑；它同時顯示新規則的取捨：記帳不再重審後，審查品質只取決於原審查，舊規則下記帳觸發的重審有時會多抓到原審查漏掉的問題。
- **候選 28b2 沒有隨報告提交回填**：reviewer 依新欄位記錄核准基線 `4ecaa4f`，但協調者保存報告的提交 `53dba91` 沒把 README 的 `待提交` 改成該 SHA。「隨報告提交回填」當時只寫在 acceptance.md，review 技能步驟 5 只列為可併入的提交類型（審查 MUST FIX 1）。S6 在步驟 5 補上回填指示，S7 的 28e、28b3 保存報告的提交都依核准基線回填。
- **候選組仍未更新 `**狀態**`**：28b 候選組的 README 狀態維持「審查中」，雖然新規則允許它隨記帳提交更新；兩組結果相同，不影響判定。

### 重跑觀察

- **改驗收時協調者會一起改計畫**：28b2、28b3 的協調者在修改 SCN 的同一提交更新計畫的證據敘述。實務上驗收變更多半伴隨計畫變更，檢查器會先擋在計畫檔；兩條路徑的結論都是重審。
- **28b3 沒有先執行檢查器**：review-evidence.md 要求一律以 `verify-artifact.py` 判定，28b3 的 agent 自行判斷需要重審，結論正確但跳過了檢查器。
- **28e 基準組重現下游回報的成本**：送審時仍是 `待提交`，舊規則下 reviewer 只為這一行判 RETURN，接著要多一個回填提交與一次完整重審；候選組在同一 fixture 上 PASS，回填併入保存報告的提交。
- **fixture 的 28b 報告前提錯誤再次被重審抓到**：28b3 的 reviewer 同樣指出「重複 id 非本次引入」不成立。這是 fixture 撰寫錯誤（見上方觀察），不影響本 issue 的判定。
