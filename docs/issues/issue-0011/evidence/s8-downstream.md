## 下游專案 B：主路徑（沒有待觀察項目）

實際 issue 是一份盤點與評估的文件 PR，合併方式是 squash，合併判定依 project.md 登記的 PR `mergedAt`。未量測的項目記在 Gate 豁免紀錄，沒有要等合併或部署的觀察。

| 觀察項目 | 結果 |
|---|---|
| `**狀態**` 的寫法 | 每次都只寫階段：待盤點 → 盤點中 → 待審查 → 修正中（review-…）→ 待審查 → 已完成。進度只寫在計畫的任務符號與證據 |
| 終態寫在哪個提交 | 最後一輪 PASS 沒有建議時，保存報告的提交同時把狀態從「待審查」寫成 `已完成`，verify-artifact 判 OK（變更區段列出狀態）。PR 開了之後收到第三方審查、選了修正，同一個提交把狀態改回「待審查」；修正後的增量覆審 PASS，保存報告的提交再寫 `已完成`。之後第三方的建議選了不修，記錄結論的記帳提交 verify-artifact 判 OK，PASS 沿用 |
| 合併前問 dev-cycle | 回報待合併：分支上的 `已完成` 沒有命中結案列，沒有改欄位 |
| 合併判定 | squash 後分支提交不在主幹歷史，用祖先關係會判未合併；PR `mergedAt` 一次判對 |
| 合併後主幹的記帳提交 | 沒有：主幹在合併前的最後一個提交之後只有 squash 提交，主幹上的 README 已是 `已完成`、`**現行 review**` 指向最後一份報告。同一專案前一個 issue 合併後補了 3 個記帳提交 |
| 合併後問 dev-cycle | 回報結案：PR 已合併，未執行的量測都在豁免紀錄，沒有待觀察項目；查詢沒有產生提交 |
| 核准 commit | 修訂規格並重新核准的提交寫不出自己的 SHA，維持「待提交」，下一個本來就要做的證據提交回填；舊基線記在 Timeline |

摩擦：

1. project.md 的合併判定寫「對照 README 狀態欄記載的 PR 編號與日期」，2.7 起狀態不記 PR 編號，這次靠分支名稱與 headRefOid 找到 PR。
2. 在同一個提交修訂並重新核准時寫不出新基線的 SHA，只能先寫「待提交」再回填。
3. 「待審查」與「審查中」的分界、RETURN 期間 `**狀態**` 寫什麼，規則沒有明說；session 寫「修正中（review-…）」。
4. PASS 附建議而使用者選修正時，每次修正都多一輪審查：獨立審查 6 輪（1 輪 RETURN、3 輪 PASS 附建議、2 輪 PASS 無建議），另有 PR 第三方審查 2 輪。
5. PR 開了之後才收到第三方審查，狀態翻轉一次（已完成 → 待審查 → 已完成）。

## 下游專案 A：有待觀察項目（要等合併的部署後觀測）

候選版 session 跑了兩輪審查與三個記帳提交，之後中止。

| 觀察項目 | 結果 |
|---|---|
| 有待觀察項目時是否在合併前寫 `已完成` | 沒有寫，維持實際階段，理由是計畫還有部署後觀測、要等合併 |
| 上一輪 PASS 是否失效 | 依 verify-artifact 判定（docs 同步提交不屬記帳區段 → 需重審），不看狀態文字 |
| PASS 附建議 | 兩輪都一次問完；記帳提交 verify-artifact 都判 OK |
| `**狀態**` 的寫法 | 「審查通過，待決定審查建議」「審查建議處理完成，待重新審查」：階段後面接下一步（README TBD-8） |

中止原因：下游審查指出候選版 docs 放在交付分支，合併會把未發版的流程契約帶進主幹，其他 issue 合併主幹後跟著換版，合併衝突多兩處，候選版再改時重新同步會改寫歷史。使用者選合併前 revert。revert 後 HEAD 回到流程契約 2.5，下一輪只能完整審查（README TBD-7）。

其他摩擦：試用設定目錄放在 /tmp，重開機後同一個 issue 改由全域技能接手且沒有提示（之後的啟動腳本改放 ~/.cache，並在技能與候選版不同時停止）；本 issue 轉達的 `init-project.py --update` 指令漏了專案路徑參數；verify-artifact 參數用錯時也回 INVALID。

沒有驗到：合併後記等待、記錄觀察證據的提交寫 `已完成`；帶反引號的 `待提交` 回填。

## 結論

- 主路徑在一個下游實際 issue 走完：合併前寫好終態、合併後主幹沒有記帳提交、dev-cycle 合併前回報待合併、合併後依登記的合併判定結案。
- 有待觀察項目的路只驗到合併前不寫終態；合併後的推進仍只有靜態撰寫。
- 快轉合併的合併判定沒有下游案例（下游 B 是 squash）。
