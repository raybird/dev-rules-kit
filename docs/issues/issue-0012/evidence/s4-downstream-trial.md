## 觀察項目

1. **處理建議後的增量覆審只查修正（SCN-001）：符合。** 第 2、3 輪逐項確認上一輪的建議，查核範圍是被改函式的呼叫端、mock 了被改模組的測試、被搬移函式的所有 import，並在新 HEAD 重跑整組回歸；沒有重查架構、安全與第 1 輪的失敗面。兩輪各一項新的 NICE TO HAVE，都標「增量引入」，沒有對沒動到的內容提新建議。
   - **建議連鎖**：第 2 輪的 NICE TO HAVE 是第 1 輪建議的重構留下的（一組工具函式分在兩個檔）；照它搬檔後，第 3 輪的 NICE TO HAVE 是同一個問題換個形式又出現（另一個函式沒跟著搬），reviewer 在報告裡也這樣寫。兩項都只影響閱讀。規則允許增量引入的建議，擋不住這種連鎖；這次收斂是因為使用者第 3 輪選不修。從第一次 PASS 到收斂 2 輪增量覆審，總共 3 份報告。
2. **增量覆審的報告（SCN-004）：符合。** 第 2 輪有「其餘沿用 review-cea3394.md」，第 3 輪有「其餘沿用 review-b672b81.md（及它沿用的 review-cea3394.md）」。本機報告都沒有 Review artifact 行，PASS 後只有一句提醒。篇幅：第 2 輪仍有完整的驗收表、失敗面與逐項確認表，都屬本輪查核；少掉的是重寫上一輪的結論，第 2、3 輪分別比第 1 輪小 28%、47%。第 2 輪另在「豁免、待確認與限制」寫了兩條流程提醒（保存報告時要改的欄位、狀態括號的寫法）。
3. **格式與措辭問題（SCN-006、SCN-007）：符合。** 第 1 輪兩處文件與程式行為不一致（計畫寫的例外處理與實作不符、README 涉及檔案寫錯職責所在），分別列 SHOULD FIX、NICE TO HAVE；第 2 輪把 `**狀態**` 括號內寫了說明文字列為流程提醒，並寫明不影響 dev-cycle 判定。沒有發現會讓 gate 判斷錯誤卻被降成建議的問題；reviewer 每輪核對核准 commit 是否為祖先、Gherkin 區塊未改、待確認事項格式。
4. **沒動到的內容有 MUST FIX 等級的問題（SCN-003）：沒有驗到。** 增量覆審兩輪都沒有這類問題。第 3 輪提到一個 BASE 就存在的現象，寫明不是這次造成，沒有列為問題。第 1 輪（完整審查，不在本規則範圍）把一個 BASE 就存在、要兩人同時手動操作才會發生的正確性問題列 NICE TO HAVE 加 `需決策`，並寫明起點程式結果相同。
5. **帶進流程契約 2.7 的改動：小困擾 1 次。** 修正提交把狀態寫成「實作中（修正上一份報告的建議）」，第 2 輪 reviewer 指出括號只放日期、SHA 這類錨定事件；不影響判定，下一個記帳提交覆寫掉。「`已完成` 在合併前寫好」沒有驗到（試用沒有進到合併，這個 issue 合併後還要部署）。下游 project.md 的合併判定段落仍描述合併後補狀態的提交，與 2.7 的方向不同；那是專案客製層，`--update` 不改，回報給下游使用者自行對齊，不是 kit 的缺陷。
6. **其他：** 增量覆審的派工只要給上一份報告、增量範圍與選了修正的建議，第 2、3 輪各約 6 至 7 分鐘；依流程契約 2.7，不受影響的結論同樣可以寫為沿用，但 reviewer 可以對沒動到的內容提新建議，報告也要照完整格式重寫已查核維度。每修一輪仍要修正提交、派增量覆審、記帳提交、verify-artifact，並問使用者一次要修哪些建議；這次 3 輪共問 3 次。試用 session 建議「只改註解或文件、不改行為」的修正走更輕的確認，記為後續評估，不是候選版的缺陷。

## 結論

SCN-001、SCN-004、SCN-006 的規則在下游實際 issue 照設計運作，報告都通過 verify-artifact；SCN-003 沒有驗到，維持僅靜態撰寫。收斂靠使用者在建議連鎖中選擇不修，規則本身沒有讓 reviewer 停止對修正提出 NICE TO HAVE。2026-11-24 使用者決定建議連鎖只記錄在本檔，不改規則、不另開 issue 追蹤（README TBD-5）。
