# Issue 0020 - 審查報告只留在開發分支，合併前刪除 (Small)

## 概述

原提案（GitHub #20）：審查報告 `docs/issues/issue-{ID}/review-{SHA}.md` 合併後留在主幹，提案認為合併後幾乎沒人回頭看，主張開發期間留在分支、合併前刪除，主幹只留連結。

2026-11-25 向下游專案調查的結果：大部分報告合併後確實沒人讀，但事先無法知道哪一份會被引用，而被引用的那些是交接、地雷紀錄與程式註解的證據來源；報告留在主幹沒有造成錯誤結論。依本 kit 範圍規則（需有下游實際發生的問題才新增規則），本 issue 判定不修復，不改規則、技能或檢查工具，只在根目錄 AGENTS.md「刻意不管」表記下本決策與重新評估條件。

**現行 review**: review-39ff6ce.md

## 決策紀錄

- 判定來源：2026-11-25 使用者在逐題確認中選「不修復」。之前同日先選「先問下游再決定」，調查結果見下節。
- 理由：六個下游專案都沒有「報告留在主幹而造成錯誤結論」的紀錄。唯一一起把舊報告內容誤引用的案例，起因是引用時沒分辨報告裡標為推論與實測的內容；報告不在工作樹時這次誤引用不會發生，但同一批報告的正確引用也會一併失去，而且這次已由下一輪審查更正。六個專案合併後都有 agent 回頭讀報告，用途與依賴見下節。移出主幹會讓這些引用失效，而多數下游主要不開 PR／MR，除了 Git 歷史沒有其他副本。
- 殘餘影響：報告繼續在主幹累積（調查時各專案 52～399 份，本 repo 63 份）。調查中提到的成本有三項：同一個 issue 有多份報告時要讀完才知道哪份是最終結論，這已由流程契約 2.5 的 `**現行 review**` 處理；rebase 改寫 SHA 後，報告檔名與其中的 Reviewed SHA 指向主幹上不存在的提交，下游要另加註對照；舊報告裡的數值會過時，有一例寫的保留天數在之後已變更，讀者改從其他來源查證，沒有因此做錯。rebase 那項是已經發生的額外工夫，過時數值那項是差點出事，都沒有達到重新評估的門檻。
- 追蹤：無。重新評估的條件是下游實際出現一次「舊報告留在工作樹而造成錯誤結論或搜尋干擾」的案例，記在根目錄 AGENTS.md「刻意不管」表。

## 調查

2026-11-25 以跨 session 訊息請六個下游專案的主 worktree 唯讀回答四題：有沒有被舊報告誤導、合併後誰回頭讀過與用途、報告不在工作樹會失去什麼、合併方式與是否刪分支。六份都回覆，只依 repo、Git 歷史與專案記憶回答。

| 項目 | 結果 |
|---|---|
| 被舊報告誤導或多花工夫 | 6／6 沒有因報告位置造成錯誤結論的紀錄；差點出事與額外工夫見上節殘餘影響 |
| 合併後回頭讀報告 | 6／6 有，都是 agent 在工作樹以搜尋或相對連結找到；有一個專案約 55 份中約 50 份沒被任何文件引用 |
| 用途 | 地雷紀錄與交接文件的原始證據；程式註解與測試引用報告編號說明為什麼這樣寫；後續審查引用實測數據；後續 issue 的需求來源與遺留項；懸置掃描依 PASS 報告補回漏記的任務狀態 |
| 報告的其他副本 | 四個專案主要不開 PR／MR，報告只在 repo；有專案以 squash 合併的 issue 原始分支已不存在，報告只剩主幹這一份 |
| 合併方式與分支 | rebase 後快轉、本機 --no-ff、平台 squash、平台 merge commit 都有；明確保留已合併遠端分支的只有兩個專案，其餘遠端沒有 issue 分支、多數已刪或只在本機合併，報告常常只剩主幹一份 |

本 repo 自身也有依賴：報告以外有 18 個 Markdown 檔以相對連結指向 issue 報告（其中 3 個在 issue 目錄外），刪掉全部 63 份後 check-links 回報 109 個斷連結。這是移出主幹要處理的代價，原提案的設計點 3 已列出。

順帶觀察：部分要長期保存的知識（地雷、實測數據、遺留項目）只寫在報告裡。部分下游已用 document-types.md「地雷紀錄」把需要常駐的內容升級出來，報告作為證據來源；也有專案的遺留項目只寫在報告。這屬各專案的收尾習慣，本 issue 不另行處理。
