## 設計邊界

### 核心保障與專案覆寫

以現有權威來源釐清三種責任，不新增三層框架或將所有 Skills 重分類：

- **核心保障**：核准來源依 [acceptance.md](../../agents/acceptance.md)，驗證與真實證據依 [verification.md](../../agents/verification.md)，獨立審查依 [review-evidence.md](../../agents/review-evidence.md)。Skill 引用定義；issue 記錄本次決策與證據，不再複寫整套 gate。
- **工作方式**：提問、掃描分類及回報屬本輪可調整範圍，維持可觀察結果與完成判準。
- **專案客製**：project.md 可調整掃描範圍、合併依據、文件債與排除判定；不能藉排除規則隱藏已確認的必要驗收缺漏（懸置掃描列為必須處理者），或把未授權行為當成已核准。窗口未到或窗口事件無法判斷的等待狀態不是已確認缺漏，可依專案規則排除（TBD-8）。

可豁免的 gate 仍須依 [既有豁免規範](../../AGENTS.md#gate-豁免紀錄) 留下使用者明確來源、項目與殘餘風險；專案客製本身不是豁免。誠實回報始終適用，未測或未獨立審查不能寫成通過。三層架構是否值得獨立調整，待本輪數據後再評估，不預先建立新 issue。

### 提問的選擇標準

問題彼此獨立、能簡短回答、答案不影響後續問題，且使用者未要求逐題時，預設合併提問。問題需要較多背景或取捨才能回答，或答案會改變後續決策時，逐題確認；使用者的明確偏好優先。不以固定問題數量作為合併條件。

### 追蹤判定的可重現性

判定順序為既有結構化資料 → 明確 issue／文件引用 → 語意補充 → 不確定時揭露。只使用現有掃描欄位，不要求新增 schema 或追蹤設定。

結構化資料缺漏或 `tracking: null` 代表尚無可用結構化去向，可回查原始結論；不能單憑此值認定沒有追蹤。去向仍需可確認存在。不追蹤理由須具體、與交付範圍相關，並說明為何無需後續處理；「這個不重要」或「以後再說」不構成有效理由。存在未豁免的必要 gate 缺漏時，不追蹤理由不能代替明確豁免，該缺漏仍須列出。

資料互相衝突、目標含糊或無權限確認時列資訊不足，附來源及不確定原因，不能任選一個來源當完成。相同證據應得到相同結論，基準案例需覆蓋這些分支。

### 掃描的行動層級

九類偵測原因保留為診斷依據，對使用者依下列層級回報，同項保留其原因與證據位置，不增加 issue 狀態或機器輸出 enum：

| 行動層級 | 判定依據 |
|---|---|
| 必須處理 | 已確認影響交付或尚未滿足且未豁免的必要 gate |
| 建議整理 | 只有文件、狀態或追蹤紀錄需要補整，未確認影響交付 |
| 無法判定 | 缺少平台資訊、證據不足或來源衝突，無法確認真實狀態 |

同一項已有確定的交付缺漏時，仍列必須處理，其他未知另行揭露。單純平台 open／README 不一致，不足以自行判定違規；缺少資訊也不自動代表已完成或有交付缺失。保留必要事實與下一步，版面可隨結果數量調整。

```gherkin
Feature: 減少形式限制並維持必要流程保障

  Scenario: 提問依相依性與使用者偏好安排

  @SCN-002
  Scenario: 依追蹤內容判斷而非只看前綴
    Given 兩份結論指向同一個已確認存在的後續 issue，只有其中一份使用「追蹤：」
    When 執行懸置掃描
    Then 兩份都不因缺追蹤而被列出
    And 不追蹤理由具體、與交付範圍相關且說明無需後續處理時，不因缺前綴而被列出
    And 空泛或延後處理的說法不構成有效不追蹤理由
    And 存在未豁免的必要驗收時，不追蹤理由不能消除該驗收缺漏
    And 先使用有效的結構化資料，再確認明確引用，最後才以語意補充判定
    And 結構化欄位缺漏時可查原文，來源衝突或無法確認時揭露資訊不足
    And 沒有去向或不追蹤理由、只有模糊承諾或不可確認目標的對照項仍揭露缺漏或未知

  @SCN-003
  Scenario: 區分交付待辦、文件差異與未知資訊
    Given 同時存在必要驗收未執行、單純文件狀態落差、平台狀態未知的 issue
    When 查詢懸置事項
    Then 保留九類偵測原因，各項依實際影響呈現必須處理、建議整理或無法判定及下一步
    And 文件差異不自動升格為阻塞，也不要求固定分段、字數與版面
    And 未執行的必要驗收不因放寬格式而消失，未知資訊不被當成完成
    And 正常進行中的 issue 不被列為異常，專案判定規則仍優先
    And 專案排除規則不隱藏已確認而未豁免的必要驗收缺漏
    And 查詢前後文件、Git HEAD 與平台狀態保持不變

  @SCN-004
  Scenario: 減法有前後證據且沒有削弱核心保障
    Given 基準與候選規則使用同組 fixture 和可比較的宿主設定
    When 比較提問與掃描結果
    Then 獨立短題合併案例的人工回覆次數下降，等價追蹤寫法不再誤報
    And 有相依決策、未授權行為、真正缺追蹤、待驗收與專案客製等對照仍正確處理
    And 任一必要 gate 漏檢都判定回歸失敗，不能以互動減少交換
    And 記錄錯誤阻塞、誤報、必要 gate 漏檢與重複維護位置，揭露未測分支
```

## 風險與首要驗證

- **最大風險**：放寬形式限制時漏掉未授權行為、真正未追蹤事項或尚未執行的必要驗收。
- **風險等級與理由**：Medium；範圍有界且可回復，仍有重要行為未知。第一輪保留核心保障，不以字數下降推論流程改善。
- **首要驗證**：規則修改前，在隔離 fixture 以基準規則建立行為紀錄，對照等價格式與實質缺漏。
- **選擇理由**：最大未知是現有規則保護範圍，同組前後行為對比最直接，無需另建端到端整合系統。
- **完成證據**：fixture、規則 SHA、宿主／模型與設定、輸入及完整輸出、實際回覆次數、逐項預期與判定。修改後同組比較；必要保障對照須全部正確，環境差異或未測分支明列。
