# Issue 3102 - 待辦到期提醒 (Small)

## 概述
讓每個待辦可以設定到期時間（精確到分鐘）；每次執行 `todo.py` 指令時檢查，未完成且已到期的待辦在指令輸出前顯示提醒。不使用常駐程序。到期時間一律以 UTC 儲存，顯示時轉成本機時區。

## 涉及檔案
- `todo.py` - 新增 `due` 指令、到期檢查與提醒輸出、列表顯示到期時間
- `test_todo.py` - 驗收測試
- `README.md` - 使用說明補上 `due` 指令（常青文件，依 project.md）

## 驗收條件

以下範例假設本機時區為 Asia/Taipei（UTC+8）。

1. **AC-1**：執行任何 `todo.py` 指令（`add`、`done`、`due`、列出）時，若有未完成且已到期的待辦，每筆先輸出一行 `⏰ 已到期：<id>. <標題>（<本機時間 YYYY-MM-DD HH:MM>）`，再輸出指令本身的結果。檢查時機在指令修改資料之後、輸出之前；不啟動常駐程序 — 檢查方式：固定「現在時間」與時區，執行各指令，斷言輸出開頭為提醒行
   - 失敗路徑：沒有已到期的未完成待辦時，不輸出任何提醒行，指令輸出與變更前相同；以 `done <id>` 完成已到期的待辦時，該次輸出不提醒該筆
2. **AC-2**：`python3 todo.py due <id> <YYYY-MM-DD HH:MM>` 將輸入視為本機時間，轉成 UTC 後存入 `todo.json` 的 `due` 欄位（格式 `YYYY-MM-DDTHH:MMZ`）；對已有到期時間的待辦再次執行即覆蓋 — 檢查方式：在 Asia/Taipei 執行 `due 1 2026-10-18 09:00`，斷言 `todo.json` 中該筆 `due` 為 `2026-10-18T01:00Z`
   - 失敗路徑：見 AC-5
3. **AC-3**：列表中設有到期時間的待辦以本機時區顯示為 `[ ] 2. 寫週報（到期 2026-10-18 09:00）` — 檢查方式：存入 `2026-10-18T01:00Z`，在 Asia/Taipei 下斷言 `render` 輸出
   - 失敗路徑：未設定到期時間的待辦，顯示與現行完全相同；顯示 UTC 時間（`01:00`）即判定失敗
4. **AC-4**：現在時間大於或等於到期時間（以同一時間點比較）即視為已到期；已完成的待辦不提醒；未完成的已到期待辦在每次執行指令時都會重複提醒 — 檢查方式：固定現在時間，測試到期前一分鐘、恰好到期、已到期但已完成三種情況
   - 失敗路徑：到期前一分鐘出現提醒，或已完成的待辦出現提醒，即判定失敗
5. **AC-5**：時間格式不符合 `YYYY-MM-DD HH:MM`，或 id 不存在時，stderr 輸出錯誤訊息、exit code 為 1，`todo.json` 內容不變 — 檢查方式：執行 `due 1 2026/10/18`、`due 99 2026-10-18 09:00`，斷言 exit code、stderr 與檔案內容沒有變動
   - 失敗路徑：寫入資料或以 exit code 0 結束，即判定失敗
6. **AC-6**：沒有 `due` 欄位的既有 `todo.json` 不需轉換，照常讀取、列出、完成，輸出與變更前相同 — 檢查方式：以舊格式資料執行列出與 `done`，斷言輸出與變更前錄下的結果一致
   - 失敗路徑：讀取舊資料時發生例外，或列表輸出有任何差異

## 風險與首要驗證

- **最大風險**：既有 `todo.json` 沒有 `due` 欄位，新程式讀取或列出舊資料時發生錯誤或輸出改變（使用者的實際資料不在 repo 中，無法盤點）
- **風險等級與理由**：Medium — 會破壞既有行為，但只限單一 CLI，失敗可以回復，也不會遺失資料。時區轉換屬標準函式庫的行為，以固定 TZ 的測試涵蓋（AC-2、AC-3），不另做前置探測
- **首要驗證**：主要實作前，先為舊格式資料的列出與 `done` 寫好 characterization test，並確認在現行程式上是綠燈（步驟 1）
- **選擇理由**：最大風險是破壞既有行為。先固定現行輸出，就能直接偵測回歸，不需要先完成端到端流程
- **完成證據**：步驟 1 的測試在變更前後都是綠燈，並記錄執行的命令與輸出
