# Issue 3103 - 待辦刪除與復原最後一次刪除 (Small)

## 概述
為 todo CLI 新增 `delete <id>` 刪除項目，以及 `undo` 復原最近一次刪除。刪除的項目不讓出 id，復原後內容與位置與刪除前相同。

## 涉及檔案
- `todo.py` - 新增 `delete`、`undo` 指令與錯誤處理
- `test_todo.py` - 既有行為保護網與 AC-1～AC-4 測試
- `README.md` - 常青文件：使用說明補上 `delete`、`undo`

## 驗收條件

1. **AC-1**：`python3 todo.py delete <id>` 後，該項目不再出現在列表，其餘項目不變；stdout 印出 `已刪除 {id}. {標題}（可用 undo 復原）` — 檢查方式：`python3 -m unittest -v` 中標注 AC-1 的測試（列表 1、2、3 刪除 2 → 列表只剩 1、3，輸出字串相符）
   - 失敗路徑：被刪項目仍顯示、其他項目的 id／標題／完成狀態被改動，或輸出字串不符，即判定失敗。
2. **AC-2**：`python3 todo.py undo` 復原最近一次刪除的項目，id、標題、完成狀態與列表位置均與刪除前相同；stdout 印出 `已復原 {id}. {標題}`。刪除後執行過 `add`、`done` 仍可復原；連刪 A、B 後 `undo` 只復原 B，再次 `undo` 不復原 A（依 AC-4 報錯） — 檢查方式：`python3 -m unittest -v` 中標注 AC-2 的測試（以已完成項目刪除後 `undo`，比對列表輸出與刪除前完全一致；連刪兩筆的情境）
   - 失敗路徑：復原後 id、標題、完成狀態或位置任一與刪除前不同，中間的 `add`／`done` 使其無法復原，或第二次 `undo` 救回了 A，即判定失敗。
3. **AC-3**：被刪除項目的 id 不會被新項目重用。列表 1、2、3 刪除 2 後 `add` 新項目，新項目 id 為 4；之後 `undo`，列表為 1、2、3、4 且 id 皆唯一 — 檢查方式：`python3 -m unittest -v` 中標注 AC-3 的測試
   - 失敗路徑：新項目取得 2 或 3 等既有／待復原 id，或 `undo` 後出現重複 id，即判定失敗（最大風險）。
4. **AC-4**：`delete` 指定不存在或已刪除的 id，或沒有可復原的刪除時執行 `undo`，stderr 印出錯誤訊息、exit code 為 1，且 `todo.json` 內容不變 — 檢查方式：`python3 -m unittest -v` 中標注 AC-4 的測試（比對執行前後 `todo.json` 位元組相同、exit code 為 1）
   - 失敗路徑：exit code 為 0、沒有錯誤訊息，或 `todo.json` 被改寫，即判定失敗。

## 風險與首要驗證

- **最大風險**：刪除後資料無法完整復原，或因 `add` 以 `len(items) + 1` 編號而重用被刪項目的 id，造成重複 id 或復原錯項——兩者都會造成待辦資料永久遺失或錯亂。另需確保既有 `todo.json`（純 list 格式）在改動後仍可讀取。
- **風險等級與理由**：High — 刪除是破壞性操作，涉及資料損失；既有 `todo.json` 若因格式變更無法讀取，影響所有既有資料。
- **首要驗證**：先以 characterization test 鎖住既有 `add`／`done`／列表行為與既有 list 格式 `todo.json` 的讀取，於未改動的 `todo.py` 上取得綠燈；再寫 AC-2、AC-3 的刪除 → 新增 → 復原往返測試並取得紅燈，才開始實作。
- **選擇理由**：最大失敗後果是既有資料與 id 一致性被破壞；回歸保護網與往返測試直接檢驗「資料是否完整、id 是否唯一」，比手動試用更可重複。
- **完成證據**：步驟 1 的保護網在改動前後同為全綠；AC-2、AC-3 測試先紅後綠，命令與輸出記錄於步驟完成證據及 `## 驗證`。
