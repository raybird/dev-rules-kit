# Issue 規模與風險雙軸設計規格

**日期**：2026-07-22\
**狀態**：已實作

## 背景

現行流程使用 Small、Medium、Large 單一分級，同時承擔文件規模、任務拆解與風險排序等意義。這會讓「修改範圍小但後果嚴重」與「修改範圍大但行為明確」的任務難以準確表達。

此外，現行規則雖已說明垂直切片只是風險優先的手段，Agent 仍可能先選擇垂直切片，再回頭替選擇補理由，將「風險優先」誤讀成「一律端到端實作」。

本設計將評估拆成「規模」與「風險」兩軸，並加入先辨識未知、再選驗證手段的決策順序。

## 設計目標

1. 規模只決定文件數量、任務清單來源及是否需要 `decompose`。
2. 風險只決定實作步驟順序、首要驗證手段及必要證據。
3. 防止 Agent 將垂直切片視為風險優先的預設答案。
4. 保持 Small 與 Medium 的輕量流程，不因高風險自動增加文件。
5. 沿用既有 `**分級**` metadata，避免破壞既有 issue 的流程判定。

## 雙軸模型

### 規模軸

沿用 `**分級**` 欄位與既有定義：

| 規模 | 文件與任務清單 | Decompose |
|---|---|---|
| Small | README 的「實作與驗證步驟」 | 跳過 |
| Medium | `implementation-plan.md` 的「實作步驟」 | 跳過 |
| Large | 完整分析文件與 Implementation Plan | 需要 |

規模評估只反映修改範圍、結構複雜度與工作量，不因風險高低自動升降級。

### 風險軸

README metadata 新增 `**風險**` 欄位：

| 風險 | 判定原則 | 規劃要求 |
|---|---|---|
| Low | 行為與依賴明確、影響侷限、容易回復 | 可依一般相依順序實作與驗證 |
| Medium | 存在一項重要未知，或失敗會造成有限度返工與影響 | 將降低該風險的驗證排在主要實作前 |
| High | 涉及資料損失、安全或權限、不可逆操作、廣泛影響，或核心外部行為尚未確認 | 第一個步驟或 Phase 必須先取得能解除最大風險的證據 |

不採計分制。只要符合較高等級的任一關鍵條件，就採較高風險，並以文字記錄判定理由。

風險不改變文件產出規格。例如 Small + High 仍只建立 README，但 README 的第一個實作與驗證步驟必須先降低最大風險。

## 風險優先決策流程

規劃 Small／Medium 的實作步驟或 Large 的 Phase 時，必須依序完成：

1. 指出最大的未驗證假設或最嚴重的失敗後果。
2. 判定風險為 Low、Medium 或 High，並寫出理由。
3. 根據風險來源選擇首要驗證手段。
4. 定義可判定風險已解除或降至可接受程度的證據。
5. 完成上述判斷後，才排列後續實作步驟或 Phase。

文件中應明確記錄：

- **最大風險**：目前最可能使方案失敗或造成嚴重後果的事項。
- **首要驗證**：在主要實作前要執行的驗證活動。
- **選擇理由**：為何該手段最直接降低最大風險。
- **完成證據**：可觀察、可重複確認的結果或通過條件。

## 驗證手段選擇

| 風險來源 | 優先手段範例 |
|---|---|
| 外部 API、套件或服務契約未知 | 契約驗證、最小真實請求、相容性探測 |
| 既有資料樣態未知 | 資料盤點、分布查詢、小樣本 dry run |
| 效能或容量未知 | 基準測試、壓力測試、最小技術實驗 |
| 害怕破壞既有行為 | Characterization test、快照、對比腳本、回歸測試網 |
| 使用者流程或跨層整合未知 | 垂直切片，端到端跑通最窄可驗證路徑 |
| 行為、資料與依賴皆明確 | 依一般技術相依順序實作 |

此表是候選手段，不是固定對照。Agent 必須依實際最大未知選擇，不能只因任務包含 UI、API 或多層修改就直接採垂直切片。

## 防止垂直切片誤用

規則中加入以下強制提示：

> 不得先決定採用垂直切片，再回頭尋找理由。必須先辨識最大未知，只有當端到端整合或使用者行為是最需要驗證的假設時，才選擇垂直切片。垂直切片是消除未知的候選手段之一，不是預設切法，也不是風險優先的同義詞。

當 Agent 選擇垂直切片時，必須同時回答：

1. 此切片要驗證哪一項尚未確認的端到端假設？
2. 為何契約驗證、資料盤點、效能實驗或回歸保護網不能更直接降低該風險？
3. 切片完成後，要觀察到什麼證據才算假設已獲驗證？

若無法回答，應重新選擇首要驗證手段。

## 各流程責任

### `docs/AGENTS.md`

- 作為規模與風險雙軸的唯一權威定義。
- 補上風險定義、metadata 格式、決策流程與驗證手段表。
- Small 與 Medium／Large 範本都新增 `**風險**`。
- 快速檢查清單新增風險欄位與首要驗證檢查。

### `new-issue`

- 分別評估規模與風險，不以其中一軸推導另一軸。
- 將 `**分級**` 與 `**風險**` 寫入 README。
- 依決策流程產生最大風險、首要驗證、選擇理由與完成證據。
- Small／Medium 直接按風險排序可執行步驟；Large 將判斷帶入 Implementation Plan，供 `decompose` 使用。

### `decompose`

- 保持僅適用 Large。
- 在切 Phase 前先執行風險決策流程。
- Phase 1 採最能降低最大風險的活動，不預設為垂直切片。
- 選擇垂直切片時，強制回答三個防誤用問題。

### `execute-task`

- 讀取既有任務順序執行，不重新評估或改寫風險策略。
- 執行首要驗證步驟時，將完成證據記錄於 Summary。

### `dev-cycle`

- 規模仍是決定是否進入 `decompose` 的唯一依據。
- 風險不新增流程分支，避免雙軸演變成九套工作流程。

### 使用說明

- 加入 Small + High 與 Large + Low 的例子，示範兩軸互相獨立。
- 將 OAuth 範例中的垂直切片說明改為「因外部整合與端到端登入行為是最大未知，所以選擇垂直切片」，避免把手段描述成原則。

## 相容性

- 既有 `**分級**` 欄位保持不變，`dev-cycle` 的分流邏輯不需遷移。
- 舊 issue 沒有 `**風險**` 時，不憑檔案數量自動推測，因為規模不能代表風險。
- 只有在舊 issue 需要重新規劃或新增步驟時，才重新評估並補寫 `**風險**`。

## 驗證方式

以情境乾跑規則，至少涵蓋：

1. Small + Low：文案修正，依一般順序執行。
2. Small + High：單行權限判斷修正，先建立回歸保護與權限案例證據。
3. Medium + Medium：第三方套件整合，先做契約或相容性探測。
4. Large + High：資料遷移，先盤點真實資料並執行小樣本 dry run，不採垂直切片。
5. Large + High：OAuth 登入，最大未知為真實 callback 與跨層流程時才採垂直切片。
6. Large + Low：規格明確的機械式搬移，可依技術相依順序拆 Phase。

最後執行：

```bash
python3 scripts/sync-skills.py
python3 scripts/sync-skills.py --check
```

## 不在本次範圍內

- 導入風險量化分數。
- 因 High risk 自動增加分析文件或升級規模。
- 建立九種規模與風險組合的獨立工作流程。
- 將 issue metadata 改成 YAML 或其他結構化 manifest。
