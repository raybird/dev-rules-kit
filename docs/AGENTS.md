# 文件資料夾說明（AGENTS）

本文件為 `docs/` 資料夾的規範說明，協助 AI Agent 理解文件結構、命名規範與撰寫標準。

## 資料夾用途

`docs/` 資料夾用於存放專案的技術文件、議題分析、實作計劃與相關文件。每個議題（Issue）通常會有獨立的資料夾，包含完整的分析、計劃與實作記錄。

## 核心設計原則：YAGNI (You Ain't Gonna Need It)

在評估任務與建立文件時，Agent 必須嚴格遵守 YAGNI 原則：

1. **拒絕通靈需求**：僅針對當前 Issue 明確定義的範疇進行分析與規劃。嚴禁為了「未來可能擴充」而規劃超出範疇的資料庫 Schema、API 欄位或系統架構。
2. **避免文件過度設計**：嚴格執行下方的「文件動態分級規範」。小變更絕不產出大文件，不為了追求完整性而製造無意義的空白或重複樣板（Templates）。
3. **保持最小範疇**：在 README 的 `## 涉及檔案` 中，僅列出完成此任務「絕對必要」的涉及檔案，無關的模組不應納入評估。

## 文件動態分級規範 (Issue Document Tiering)

> **本節是 issue 規模與風險規則的唯一權威定義（single source of truth）。** `new-issue`、`dev-cycle`、`execute-task`、`decompose` 等 skill / workflow 內的說明皆為方便閱讀的摘要，若有出入一律以本節為準；調整規則時必須先改本節，再同步各 skill 摘要。

Issue 必須分別評估兩個互不推導的軸：

- **規模（`**分級**`）**：只決定文件數量、任務清單來源及是否需要 `decompose`。
- **風險（`**風險**`）**：只決定實作順序、首要驗證手段及必要證據，不改變文件數量。

### 規模分級

為了在保障開發正確性的同時避免「小變更、重文件」的繁重負擔，文件產生應依任務複雜度動態評估（Small / Medium / Large 三級），只產出對應的必要文件：

| 分級 | 適用場景 | 產出檔案 |
|------|---------|---------|
| **輕量級 (Small)** | 單一檔案的 Bug 修正、極簡單的 feature 實作、文字/日誌/設定微調 | 僅 **`README.md`**（需求與實作步驟皆合併寫在 README 內，不另建分析與計畫檔案） |
| **中量級 (Medium)** | 局部功能的 Feature 開發、不涉及複雜架構調整的重構、多檔案但邏輯直觀的修改 | **`README.md`** + **`implementation-plan.md`**（分析併入實作計畫的前置章節，省略單獨分析文件） |
| **重量級 (Large)** | 跨多個模組/服務、新增資料庫 schema、複雜系統遷移、重大架構變更或大型功能模組開發 | 完整四件套：**`README.md`**、**`requirement-analysis.md`**、**`technical-analysis.md`**、**`implementation-plan.md`** |

分級一經評估，**必須寫入 `README.md` 結尾 metadata 的 `**分級**` 欄位**（值只能是 `Small`、`Medium`、`Large` 三者之一）。此欄位是後續流程判斷的唯一依據：

| 分級 | 任務清單來源 | 是否需要額外拆解 |
|------|-------------|----------------|
| **Small** | `README.md` 的「實作與驗證步驟」 | 否 |
| **Medium** | `implementation-plan.md` 的「實作步驟」 | 否 |
| **Large** | `implementation-plan.md` → 另行拆解為 Phase / Task | 是 |

Small 與 Medium 的實作步驟本身即為可執行的任務清單，**不應再產生額外的分解文件**（避免同一份步驟寫兩遍）。僅 Large 因跨模組、任務量大，才需要進一步拆解為 Phase / Task。

### 風險分級

風險一經評估，**必須寫入 `README.md` 結尾 metadata 的 `**風險**` 欄位**：

| 風險 | 判定原則 | 規劃要求 |
|------|---------|---------|
| **Low** | 行為與依賴明確、影響侷限、容易回復 | 可依一般相依順序實作與驗證 |
| **Medium** | 存在一項重要未知，或失敗會造成有限度返工與影響 | 將降低該風險的驗證排在主要實作前 |
| **High** | 涉及資料損失、安全或權限、不可逆操作、廣泛影響，或核心外部行為尚未確認 | 第一個步驟或 Phase 必須先取得能解除最大風險的證據 |

不採加總分數。只要符合較高等級的任一關鍵條件，就採較高風險，並記錄判定理由。**規模與風險不得互相推導**：Small + High 仍只產出 README、仍使用輕量驗收條件（強度另依「驗收標準的形式依規模決定，強度依風險決定」加強）；Large + Low 仍產出完整四件套、仍使用完整 Gherkin 並執行 `decompose`。

### 風險優先決策流程

規劃實作步驟或 Phase 時，必須依序完成：

1. 指出最大的未驗證假設或最嚴重的失敗後果。
2. 判定 Low、Medium 或 High，並寫出理由。
3. 根據風險來源選擇首要驗證手段。
4. 定義可判定風險已解除或降至可接受程度的證據。
5. 完成上述判斷後，才排列後續實作步驟或 Phase。

風險為 Medium / High 時，文件必須明確記錄「最大風險」、「風險等級與理由」、「首要驗證」、「選擇理由」與「完成證據」五項。Low 且無特殊前置驗證時，`## 風險與首要驗證` 可收斂為一行——`**風險**: Low — 無明顯未知，依一般相依順序實作與驗證`——不逐欄填寫五項樣板；實作中升級為 Medium / High 時再展開完整五項。

| 風險來源 | 優先手段範例 |
|---------|-------------|
| 外部 API、套件或服務契約未知 | 契約驗證、最小真實請求、相容性探測 |
| 既有資料樣態未知 | 資料盤點、分布查詢、小樣本 dry run |
| 效能或容量未知 | 基準測試、壓力測試、最小技術實驗 |
| 害怕破壞既有行為 | Characterization test、快照、對比腳本、回歸測試網 |
| 使用者流程或跨層整合未知 | 垂直切片，端到端跑通最窄可驗證路徑 |
| 行為、資料與依賴皆明確 | 依一般技術相依順序實作 |

此表是候選手段，不是固定對照。**不得先決定採用垂直切片，再回頭尋找理由。** 只有當端到端整合或使用者行為是最需要驗證的假設時，才選擇垂直切片。垂直切片是消除未知的候選手段之一，不是預設切法，也不是風險優先的同義詞。

選擇垂直切片時必須回答：

1. 此切片要驗證哪一項尚未確認的端到端假設？
2. 為何契約驗證、資料盤點、效能實驗或回歸保護網不能更直接降低該風險？
3. 切片完成後，要觀察到什麼證據才算假設已獲驗證？

若無法回答，應重新選擇首要驗證手段。

## BDD 驗收規格與 TDD 證據

### 驗收標準的形式依規模決定，強度依風險決定

所有 issue 都必須在 `README.md` 記錄驗收標準並取得使用者明確核准，作為單一真相來源。**形式只由規模決定**，風險不改變形式：

| 規模 | 形式 | README 章節 |
|------|------|------------|
| **Small** | 輕量驗收條件 | `## 驗收條件` |
| **Medium / Large** | 完整 Gherkin + 核准紀錄 | `## Gherkin 驗收劇本`、`## Gherkin 核准紀錄` |

這是「規模與風險不得互相推導」的直接後果。高風險需要的是**更強的證據**，不是**更繁複的格式**：把 Small + High 推去寫完整 Gherkin，等於用風險推導出文件形式，並產生文件量遠大於 diff 的失衡。

**輕量驗收條件**逐項列出可觀察結果與可重複執行的檢查方式即可，不需 Gherkin 語法、Scenario ID 與逐項核准表。風險決定它要多強：

| 風險 | 要求 |
|------|------|
| **Low** | 每項條件有編號（`AC-1` 起）、可觀察結果與可重複執行的檢查方式；該節記錄核准日期與來源 |
| **Medium / High** | 上列全部，另加三項：每項條件必須寫出**失敗路徑**（什麼情況判定失敗、失敗時的可觀察行為）；至少一項條件專門覆蓋「風險與首要驗證」所列的最大風險；該節另記 `**核准 commit**` 並套用「規格修訂的查核」 |

實作中若**風險**升級（Low → Medium / High），補齊上表的額外要求即可，不需改寫成 Gherkin。只有**規模**升級（Small → Medium / Large）才必須改用完整 Gherkin 並重新取得核准。

既有 issue 若已將 Small 任務寫成完整 Gherkin 與核准紀錄，**維持有效**，不需為符合本節改寫；此時以該 issue 實際採用的形式進行後續查核。本節只約束新建立的 issue，以及規模變更後的重新規劃。

### 完整 Gherkin 的要求

每個 Scenario 必須：

- 使用唯一且穩定的 ID（例如 `SCN-001`），供計畫、測試、review 與 PR 追蹤。
- 使用標準 `Feature`、`Scenario`、`Given`、`When`、`Then`；需要共用前置條件時可使用 `Background`，資料組合才使用 `Scenario Outline` 與 `Examples`。
- 描述外部可觀察行為，不綁定函式名稱、資料表或內部實作。
- 至少包含主要成功路徑及已知的重要失敗路徑；尚未取得共識的行為不得自行補寫。

建立或修改劇本前，必須進行蘇格拉底式澄清，一次只問一個問題；已安裝 Superpowers 時優先使用 `brainstorming`，未安裝時執行 `new-issue` 內建的等價流程。未取得核准的 Scenario 不得進入 production code 實作。

核准結果必須持久化在 README 的 `## Gherkin 核准紀錄`，包含核准 commit、可追溯的核准來源，以及**逐 Scenario** 的核准日期與狀態：

```markdown
## Gherkin 核准紀錄
- **核准 commit**: `{短 SHA}`
- **核准來源**: 使用者於 YYYY-MM-DD 對話明確核准

| Scenario | 核准日期 | 狀態 |
|----------|---------|------|
| SCN-001 | YYYY-MM-DD | 已核准 |
| SCN-002 | - | 待核准 |
| SCN-003 | YYYY-MM-DD | 待重新核准 |
```

狀態只有下列三種：

| 狀態 | 意義 | 核准日期 | 可否實作 |
|------|------|---------|---------|
| `已核准` | 使用者已明確核准此 Scenario | 取得核准的日期 | 可 |
| `待核准` | 尚未取得核准（見「分批核准」） | 填 `-` | 否 |
| `待重新核准` | 核准後劇本被修訂（見「規格修訂的查核」） | 前次核准日期 | 否 |

表中缺少任一現存 Scenario ID、或列出不存在的 ID，都視為核准紀錄不完整。`**核准 commit**` 是承載該次核准內容的 issue 文件提交；尚未提交時填 `待提交`，並在首次提交後立即回填。

**未分批時的省略形式**：所有 Scenario 於同日一次核准、沒有任何 `待核准` 或 `待重新核准` 時，逐項核准表可省略為單行：`- 全部 Scenario 於 YYYY-MM-DD 核准`。此單行視同一張涵蓋所有現存 Scenario、全部 `已核准` 的核准表，本檔與各 skill 所稱「逐 Scenario 核准表」皆包含此省略形式。之後發生分批核准或規格修訂時，再展開為逐項表格。

### 分批核准

Scenario 數量多時，**不要求一次核准全部**。逐項核准表本身即支援部分核准：尚未取得同意的 Scenario 標為 `待核准`，已同意的標為 `已核准`，issue 文件即可建立並就已核准部分進入實作。

**放行門檻**：`new-issue` 要結束，已核准的 Scenario 必須涵蓋**核心目標的主要成功路徑**，以及**澄清過程中已辨識的重要失敗路徑**。只核准邊緣案例、把主要路徑留在 `待核准`，等同沒有可實作的規格，不得放行。

分批只是延後核准時機，不是降低核准標準：

- `待核准` 的 Scenario 不得實作。`execute-task` 指定的項目對應到 `待核准` 時停止並回到 `new-issue`；其他 Scenario 為 `待核准` 不阻擋本項目。
- 進入 `create-pr` 前，核准表必須全部為 `已核准`。仍有 `待核准` 時退回 `new-issue` 補齊，或由使用者明確裁示刪除該 Scenario。
- 標為 `待核准` 必須是因為該 Scenario 依賴尚未取得的資訊或決策，並在 `## 待確認事項` 留下對應項目；不得因為問起來麻煩就標記待核准。

### 規格修訂的查核

**規格在實作中被修訂是 BDD 外迴圈的預期結果，不是違規。** 查核的目的不是阻止修訂，而是確保修訂被看見且被同意。以 git 作為獨立見證，不使用內容雜湊：

```bash
git diff {核准 commit}..HEAD -- docs/issues/issue-{ID}/README.md
```

- **無輸出，或差異未觸及 Gherkin 區塊**：所有 Scenario 維持已核准，直接繼續。
- **差異觸及 Gherkin 區塊**：逐一檢視受影響的 Scenario——
  - **條件、動作或預期結果改變，或 Scenario 增刪**：將**該 Scenario** 標為 `待重新核准`，重新進入澄清流程（Superpowers 可用時優先調用 `brainstorming`，否則使用 `new-issue` 內建流程），取得核准後更新該列的日期與狀態。未被差異觸及的 Scenario 不受牽連，維持原核准。
  - **只是措辭、排版或縮排調整**：不需重新核准，於 README Timeline 補記日期與修訂內容即可。

**Small + Medium / High 的輕量驗收條件**套用同一命令與同一判準，只是粒度較粗：差異觸及 `## 驗收條件` 區塊，且改變了任一條件的可觀察結果、失敗路徑或檢查方式時，在該條目行尾標註 `（待重新核准）`，取得核准後移除標註並更新核准日期與 `**核准 commit**`；措辭或排版調整同樣不需重新核准。Small + Low 沒有核准 commit，不套用本查核，修訂以 Timeline 記錄即可。

`**核准 commit**` 在每次重新核准後更新為新的提交。值為 `待提交` 但 README 已被提交時，先以 `git log` 找出該提交並回填，再進行查核。

修訂一律遵守本檔「Agent 工作流程與時序保留」的原則：不覆寫舊敘述，以帶日期的補充說明與 Timeline 記錄變更。判定「只是措辭調整」的責任在做出判定的 agent，`review` 會依同一份 diff 覆核。

### 雙迴圈追蹤

Medium / Large 的實作計畫必須以 Scenario ID 建立雙迴圈追蹤；Small 的任務清單只需逐步驟標注 AC 編號與驗證方式（可直接引用該 AC 的檢查方式），迴圈細節與紅綠燈證據由 `execute-task` 執行時記錄：

- **BDD 外迴圈**：Gherkin feature、Step Definitions、BDD runner 命令及預期紅燈原因。專案沒有 BDD runner 時，以標註 Scenario ID 的整合或端對端測試充當外迴圈，並在計畫記錄採用的替代方式；不得因缺少特定工具而省略外迴圈。
- **TDD 內迴圈**：驅動底層行為的單元測試、預期紅燈原因、最小 production code 與重構後回歸命令。

#### 紅綠重構證據

**本檔以「紅綠重構證據」一詞指稱下列四段的完整集合**，其他文件與 skill 直接使用此詞，不再逐一展開：

1. 外迴圈紅燈
2. 單元測試紅燈
3. 最小實作後全綠
4. 重構後全綠

每一段都必須記錄驗收標準編號、實際命令、exit code 或結果摘要，以及與目標行為相關的失敗／成功原因。只有「測試已通過」的文字、狀態符號或 commit 存在，都不構成證據。四段缺任一段即為證據不完整。

**Small 的單迴圈合併**：Small 且外迴圈與內迴圈落在同一測試層級（單一檔案修正的可觀察行為只存在於一個層級）時，可合併為單一紅綠燈——四段縮減為三段（合併紅燈、最小實作後全綠、重構後全綠），證據中必須記錄「為何此層級即為該行為的可觀察層級」。層級確實分開（另有整合面行為）的 Small 仍維持雙迴圈；Medium / Large 不適用合併。

#### 假綠燈

**「假綠燈」指以任何方式製造出不代表行為正確的綠燈**，包含但不限於：

- 刪除、略過、弱化、註解、只執行部分或改寫既有測試
- mock 掉正在驗收的核心行為、硬編碼測試資料答案、使用無實際 assertion 的測試

假綠燈一律不得作為證據。測試契約只有在核准的行為已變更、能以證據證明測試錯誤，或使用者明確要求時才可修改，且必須記錄真實理由——把上述任一情況記錄成「測試通過」即構成不實回報。

### 不改變可觀察行為的任務

紅燈要求只適用於會改變可觀察行為的任務。下列兩類依定義就不該產生失敗測試，改用等價證據：

- **純重構**（搬移、改名、抽取、格式化）：記錄「變更前」與「變更後」執行**同一組**既有測試的實際命令與全綠輸出。既有測試不足以覆蓋被重構的行為時，先補上 characterization test 並取得綠燈，再開始重構。
- **純文件、排版或無可執行行為**：以可重複的靜態檢查或明確手動步驟替代，記錄不適用理由與實際結果。

在計畫中將任務標為「不改變可觀察行為」，等同承諾其 diff 不含行為變更；review 會據此查核，發現行為變更時退回補齊紅燈證據。

### Review artifact 的存放

review 報告必須持久化成可跨 session 讀取、且綁定被審查 HEAD SHA 的 artifact。存放位置依環境擇一，不限定特定平台：

1. 專案使用的 code review 平台（GitHub PR review / comment、GitLab MR discussion、Gitea review 等）。
2. 平台不可用、無權限或純本機流程時，寫入 `docs/issues/issue-{ID}/review-{HEAD 前 7 碼}.md` 並隨變更提交。

兩者都必須包含 Reviewed HEAD SHA、獨立 reviewer 識別與流程判定。只存在於對話中的報告不構成 artifact。

### Gate 豁免紀錄

使用者明確要求跳過某項 gate 時，agent 必須照做，並在 `README.md` 建立或追加 `## Gate 豁免紀錄`：

```markdown
## Gate 豁免紀錄
- **日期**: YYYY-MM-DD
- **豁免項目**: {被跳過的 gate，例如「BDD 外迴圈紅燈」「獨立 reviewer」}
- **使用者原話**: {原始要求，不改寫}
- **殘餘風險**: {因此未被驗證的事項}
```

不得自行推定豁免：使用者沉默、時間壓力或任務看起來很小都不構成豁免理由。豁免可以跳過流程，但不得把未執行的驗證寫成已通過、未審查的變更寫成已審查，也不得把假綠燈宣稱為測試通過。

## 待確認事項

**已知的未知必須留下痕跡。** `new-issue` 允許把不影響安全範圍與首要驗證的未知記錄為待確認事項後繼續，但這類事項若只寫在對話或分析文字裡，後續流程無從追蹤，等同遺失。因此它們一律收斂到 README 的 `## 待確認事項`：

```markdown
## 待確認事項

| 編號 | 事項 | 狀態 | 影響 |
|------|------|------|------|
| TBD-1 | {待確認的問題} | 待確認 | {未確認會影響什麼；關聯的 Scenario ID 或步驟編號} |
| TBD-2 | {待確認的問題} | 已解決 | {結論與確認日期} |
| TBD-3 | {待確認的問題} | 不影響本次交付 | {判定理由} |
```

- 編號 `TBD-1` 起，穩定不重編；狀態只有 `待確認`、`已解決`、`不影響本次交付` 三種。
- 每個標為 `待核准` 的 Scenario 都必須有對應的待確認事項，說明它在等什麼。
- **這是揭露機制，不是阻擋機制**：仍有 `待確認` 項目不阻止 `create-pr`，但 `create-pr` 必須將其原文揭露為殘餘風險，由 reviewer 判斷可否合併。
- 判定 `不影響本次交付` 必須寫出理由，且該判定會被 `review` 依同一份 README 覆核；不得為了讓表格清空而改狀態。
- 沒有待確認事項時整節省略，不留空表格。

阻塞級的未知（缺少 issue ID、核心目標，或會影響安全範圍與首要驗證的決策）不適用本節——那些必須當場問到答案，不得降級成待確認事項。

## 文件類型與內容規範

各文件的用途、標記與「應包含的內容」皆以本節為單一依據（是否建立則依「文件動態分級規範」）：

### README.md（必備）

議題的入口文件。所有分級都必須包含：

- 議題概述
- 驗收標準（Small 為輕量驗收條件；Medium / Large 為具唯一 Scenario ID 的 Gherkin 與核准紀錄）
- 涉及檔案清單
- 風險與首要驗證
- 可執行步驟或其權威來源
- Timeline
- 分級、風險與狀態 metadata

Medium / Large 另須包含文件清單（連結到實際建立的文件即可）；「快速導覽」與「關鍵差異」只在有新舊行為或流程對照時撰寫（重構、遷移、行為變更類 issue），沒有對照可寫時不硬填這兩節。Small 採輕量級格式，不補入這些非必要章節。

### requirement-analysis.md（Large 適用）

應包含：
- 需求描述
- 現況分析（詳細說明現有程式碼邏輯）
- 問題點總結
- 目標

涉及檔案清單只維護在 README 的 `## 涉及檔案`，本檔不另行複寫。

### technical-analysis.md（Large 適用）

閱讀程式碼後撰寫，應包含：
- 技術可行性分析
- 方案選型與取捨
- 架構影響評估
- 實作細節與待釐清項目

### implementation-plan.md（Medium / Large 適用）

應包含：
- 設計方案（函式簽名、流程設計）
- 實作步驟（分階段，標記完成狀態）
- 使用方式對照（變更前後）
- 測試策略
- Scenario ID 對應的 BDD 外迴圈與 TDD 內迴圈（不改變可觀察行為的任務改記等價證據）
- 風險與首要驗證：引用 README 的 `## 風險與首要驗證`，不另行複寫五項欄位

## 日期規範

文件中所有日期皆以本節為單一依據：

- **日期格式**：使用 `YYYY-MM-DD` 格式（例如：2026-12-19）
- **時間來源**：**一律以系統當下的日期為準**，禁止手動指定或統一日期
  - 建立文件時，使用系統當天的日期
  - 更新文件時，使用系統當天的日期
- **建立日期**：文件初次建立的日期（系統當時日期）
- **最後更新**：文件最後修改的日期（系統當時日期）。此欄位只用於常青文件與本檔這類長生命週期文件——新鮮度標示是給讀者判斷「還能不能信」的；issue 文件範本不含此欄位，其生命週期由 `**狀態**` 欄位宣告
- **維護紀錄**：依實際變更時間記錄，**不要全部統一為同一天**
  - 例如：系統日期 12-18 建立文件、12-19 進行檔案重構，應分別記錄為 `2026-12-18` 和 `2026-12-19`
  - 每次異動都應使用該次異動發生時的系統日期

## Agent 工作流程與時序保留 (Workflow & Timeline Tracking)

在開發或是逐步推進的 Issue 中，經常會發生「文件建立時間」與「逐步實作時間」產生落差的情況。為避免後續接手人員因為「描繪舊狀態的設計文件」對比「已經開發的程式碼」而產生誤會，Agent 必須遵守以下時序保留原則：

1. **接收與理解**：閱讀 User Request，確認 issue ID 與核心目標；必要輸入不足時先詢問，不得猜測。
2. **探索與分級**：閱讀 workspace 現況，分別判定規模與風險，據此決定文件集合與首要驗證。
3. **澄清與核准**：若 Superpowers 可用則優先調用 `brainstorming`，否則執行 `new-issue` 內建流程；一次只問一個問題，將共識轉成該規模對應形式的驗收標準（Small 為輕量驗收條件，Medium / Large 為具 Scenario ID 的 Gherkin），並依風險補足強度，取得使用者核准後才繼續。
4. **初步建立**：建立 `README.md`，填寫驗收標準、metadata、已知資訊與初始 Timeline。
5. **依規模建立文件**：
   - Small：不建立其他文件，將需求、風險及可執行步驟寫入 README。
   - Medium：建立 `implementation-plan.md`，將分析概要、實作步驟與驗證寫入該檔。
   - Large：依序建立 `requirement-analysis.md`、`technical-analysis.md` 與 `implementation-plan.md`。
6. **完整性檢查**：確認實際文件集合、README 連結、驗收標準、metadata 與任務清單符合分級規範。
7. **執行與更新 (重要)**：開始 Coding 後，若發現原始分析與現狀不符，**不應直接抹除舊文件的歷史描述**，而是：
   - 在 `implementation-plan.md` 或其他文件的對應段落，使用 Github Alert 語法（如 `> [!NOTE]`）加上標有日期的補充說明，指出何時的 commit 已經改變了先前的 As-Is 狀態——這是修訂留痕的主要位置，讀者讀到該段的當下就能看到它已過時。
   - 在 `README.md` 的 `Timeline` 補記該事件與日期。Timeline 只記語意事件（建立、核准、規格修訂、merge 等）；單純完成步驟不逐筆記錄，進度由任務清單的狀態符號表示。
   - issue 文件不另行維護檔尾 `Changelog` 或「維護紀錄」——它們生命週期短、merge 後凍結，git 與上述兩處已完整留痕。

## 常青文件更新責任 (Evergreen Docs)

`docs/architecture/`、`docs/domain/`、`docs/operations/` 是**常青文件**——它們描述系統當下的樣子，不是某次 issue 的歷史快照。issue 文件寫完就凍結，常青文件則必須跟著程式碼走。

沒有明確歸屬的更新責任時，這類文件會以固定的方式腐化：內容停在最後一次有人想到要改它的那天，而讀者無從察覺它已過期——文件不會宣告自己過時，只會繼續以權威的語氣描述一個不再存在的系統。**因此責任必須綁在「什麼變更觸發哪份文件」上，不能靠自覺。**

**issue 收尾時，若本次變更動到下列任一項，必須一併更新對應的常青文件**；文件若有「最後驗證」之類的日期標頭，同時更新為系統當下日期：

| 變更內容 | 要更新的文件 |
|---------|------------|
| 部署拓撲（新增部署單元、站台、服務、機器）、環境對應 | `architecture/system-overview.md` |
| 路由掛載順序、新增／移除 API 路由群組、認證鏈或守門方式 | `architecture/projects/{對應子專案}.md` |
| 模組分層、跨頁或跨模組的狀態管理、路由結構 | `architecture/projects/{對應子專案}.md` |
| 跨模組的領域規則、實體關係、術語定義 | `domain/` 對應文件 |
| 部署流程、告警設定、事故處理程序 | `operations/` 對應文件 |
| 使用者或客戶看得到的功能異動 | 該專案的使用者文件（功能總覽、操作手冊等） |

上表是起點而非完整清單。專案有自己的常青文件時，在此表補上「什麼變更會觸發它」，讓觸發條件與文件本身一起維護——只新增文件而不登記觸發條件，等於預約了下一份沒人更新的文件。

常青文件的內容邊界（什麼該寫、什麼不該寫、防腐標頭格式）由各專案的 `architecture/README.md` 定義；本節只規定何時必須更新。

## 文件維護原則

1. **即時更新**：實作完成後應立即更新文件狀態。
2. **狀態追蹤**：使用清晰的狀態標記（見「標記符號規範」）。
3. **完整性**：確保文件涵蓋所有重要資訊。
4. **可讀性**：使用清晰的標題、列表和表格。
5. **日期準確**：所有日期依「日期規範」處理。

## 注意事項

1. **語言**：所有文件使用繁體中文（台灣）。
2. **日期**：依「日期規範」處理（格式 `YYYY-MM-DD`、以系統當時時間為準）。
3. **檔案路徑**：使用相對路徑（例如：`./requirement-analysis.md`）。
4. **程式碼區塊**：標註語言類型（例如：`typescript`、`bash`）。
5. **連結**：使用 Markdown 連結格式，確保相對路徑正確。

## 快速檢查清單

建立新 issue 文件時，確認：
- [ ] 已建立 `issue-{編號}/` 資料夾
- [ ] 已依任務分級建立對應文件（見「文件動態分級規範」）
- [ ] `README.md` 結尾 metadata 已填寫 `**分級**` 欄位
- [ ] `README.md` 結尾 metadata 已填寫 `**風險**` 欄位，且未由規模推導風險
- [ ] 已記錄最大風險、首要驗證、選擇理由與完成證據，並將首要驗證排在主要實作前（風險為 Low 且無特殊前置驗證時，一行收斂即可）
- [ ] 已用一次一題的流程完成澄清，且使用者已核准驗收標準；若使用 Superpowers，已記錄 `brainstorming` 調用
- [ ] 驗收標準的形式符合規模（Small 為輕量驗收條件，Medium / Large 為完整 Gherkin），且未由風險推導形式
- [ ] 採完整 Gherkin 時：核准紀錄包含核准 commit、核准來源，以及涵蓋所有現存 Scenario 的逐項核准表（或未分批時的單行省略形式）；每個 Scenario 有唯一 ID、標準 Given / When / Then 與可觀察結果
- [ ] 分批核准時：已核准的 Scenario 已涵蓋核心目標的主要成功路徑與已辨識的重要失敗路徑，且每個 `待核准` 項目都有對應的待確認事項
- [ ] 採輕量驗收條件時：每項條件都有可觀察結果與可重複執行的檢查方式，並記錄核准日期與來源
- [ ] Small 且風險為 Medium / High 時：每項條件都寫出失敗路徑，至少一項覆蓋最大風險，並已記錄核准 commit（或 `待提交`）
- [ ] 已知的未知已寫入 `## 待確認事項` 並標明狀態與影響；阻塞級未知已當場取得答案，未被降級成待確認事項
- [ ] Medium / Large：實作步驟已將每項驗收標準映射至外迴圈、內迴圈與紅綠燈證據；Small：任務清單逐步驟標注 AC 編號與驗證方式；不改變可觀察行為的任務已改記等價證據與理由
- [ ] 若有使用者明示豁免，已建立 `## Gate 豁免紀錄` 並填寫日期、豁免項目、使用者原話與殘餘風險
- [ ] 文件內容涵蓋對應章節（見「文件類型與內容規範」）
- [ ] 日期皆為系統當下日期、格式 `YYYY-MM-DD`（見「日期規範」）
- [ ] Timeline 記錄了各語意事件（建立、核准、規格修訂等）的實際日期，沒有逐步驟流水帳
- [ ] 文件連結路徑正確
- [ ] 狀態標記清晰
